# dt bug：队列严格先进先出，钉在空闲节点的任务被排在前面、等待另一节点的任务阻塞

- 报告日期：2026-09-05
- 来源：本机 star-0 作为 dt 头节点（center `headstar`），`dt 0.13.6 (git 74a5abe1bcda)`
- 严重程度：中（多项目共用一个调度中心时，一个节点空闲而任务排不上）

## 现象

队列中依次有：4 个别项目的任务（需要 1 张 gc6d 的 GPU，而 gc6d 两张卡都在跑任务），然后是本项目的任务 `lrd-w1-star0-CF`（`-g 0 --node star-0`，不需要 GPU，且 star-0 与 gc6d 无关）。后者一直 queued，`dt info` 给出：

```
status  queued waiting: FIFO capacity is reserved for earlier job 20260905-1906_vt-winopen-s5-001-dt_train_victims_58eb416a80b3f0fc
```

即调度器把队首任务未能满足的容量当作全局约束，后续任务即使目标节点不同、资源可立即满足，也不会被派发。

## 期望

按节点（或按资源匹配）做队列推进：队首任务因节点 X 无容量而等待时，不应阻塞只需节点 Y 容量的后续任务。至少对显式 `--node` 钉定的任务，按节点分别维护 FIFO。

## 影响

本项目按用户要求把 star-0 的 GPU 用起来，但只要别的项目在 gc6d 前面排着队，star-0 就永远排不上；本次只能把 star-0 的这一波改为绕开 dt 直接运行（本机即头节点），失去 dt 的跟踪。

## 附带观察

- `dt free` 的空闲判定要求 GPU 上无任何进程：star-0 上常驻的 rustdesk（远程桌面，424 MiB）使该卡永远"忙"。建议提供节点级的进程忽略列表（按进程名或用户），或把"显存 < 阈值 且 利用率 < 阈值"视为空闲。
- 三个同路径不同名的项目（`lrd-online-clean` / `-b` / `-c`）被用来绕开"同一环境的任务串行"的锁，说明环境锁的粒度值得重新考虑（同一环境的只读并发使用应当允许）。
